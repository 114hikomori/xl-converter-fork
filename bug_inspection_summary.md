# Investigation and Debugging Summary: xl-converter-fork

## 1. Inspection Areas & Findings

### PNG Lossy Quality Setting (`pngquant`)
- **Location:** `core/worker.py` (`Worker.convert`), `output_tab.py`, `settings_tab.py`, and CLI binary `bin\win\pngquant\pngquant.exe` (v2.17.0).
- **Inspection:** Evaluated whether `--quality=0-N` parameters were parsed properly by `pngquant` or ignored by UI state logic.
- **Finding:** CLI behavior verified on real-world complex images (626k+ colors). Output sizes scale properly between quality settings (e.g., q10 = 1.45 MB vs q90 = 2.71 MB). Initial flat results were due to testing on a low-color sample image (`sample.png`) which converged to identical palettes. End-to-end integration within `Worker.convert` operates as intended.
- **Follow-up (2026-08-31), not a bug:** A `compare-image`-tool `preflight.json` run against `_sample_img\real_sample` flagged 32 content groups where the app's own PNG lossy80/90/95 outputs were byte-identical, raising doubt about the "operates as intended" finding above. Re-verified by running `pngquant.exe` directly at quality 60/80/90/95 on 4 of the flagged `real_sample` files. The quality parameter does keep varying correctly (q60 differs from q80/90/95 on every file; on a lower-complexity control file 02_CP01.png, q80/90/95 also stay distinct: 18/28/40 colors, Q83/93/95). But on the 3 high-complexity photographic files tested (500k+ unique colors, e.g. `01_CP00.png`, `31_CP30.png`, `44_44.png`), q80/90/95 converge to byte-identical output because pngquant saturates PNG's hard 256-entry `PLTE` palette cap (confirmed against the PNG spec itself) — no encoder can add palette entries the 8-bit indexed format doesn't have room for. Cross-checked `31_CP30.png`'s hash from this direct pngquant run (`2B86D58858BA`) against preflight.json's own recorded hash for the same file across the same 3 variants — exact match, confirming this is real, reproducible pngquant behavior, not a `compare-image` artifact. Other palette-based lossy-PNG tools (pngnq/pngnq-s9, TinyPNG, exoquant) hit the identical ceiling for the same reason (verified via each tool's own docs) — this is a PNG-format limit, not a pngquant- or xl-converter-specific defect, so no code change was made. Worth surfacing to users (e.g. a note that PNG lossy quality above ~80 has little/no effect on busy photos already at the palette cap) rather than treated as a bug to fix.

### Windows `SetFileTime` Failure Masking (`core/timestamps.py`)
- **Location:** `core/timestamps.py` (`_win32_handle`, module-level `kernel32 = ctypes.WinDLL(...)` setup).
- **Inspection:** Empirically tested `getTimestamps`/`applyTimestamps` end-to-end (real files on this machine, not just code reading). The happy path (copy timestamps from a real source file onto a real destination file, including creation time via the Win32 `SetFileTime` path) round-tripped all three timestamps exactly. Then tested the failure path directly: called `_win32_handle()` on a path that does not exist.
- **Finding: Confirmed Bug.** `_win32_handle()` is supposed to raise `ctypes.WinError(...)` immediately when `CreateFileW` fails (`if handle == INVALID_HANDLE: raise ...`), but the empirical test on a nonexistent path shows it does **not** raise — it silently yields a handle value of `-1` (verified: `unexpected_success: true, handle: -1`). Root cause: `kernel32.CreateFileW` (and `SetFileTime`/`CloseHandle`) have no explicit `.argtypes`/`.restype` set, so ctypes defaults the return type to a 32-bit `c_int`. The real Win32 `INVALID_HANDLE_VALUE` is a 64-bit all-ones value; truncated to `c_int` it round-trips to Python `-1`. But `INVALID_HANDLE = wintypes.HANDLE(-1).value` is computed through the pointer-sized `HANDLE` type, producing a different value — so `handle == INVALID_HANDLE` is `False` even when `CreateFileW` genuinely failed, and the check never fires. Downstream, `SetFileTime(-1, ...)` then fails too (an exception does eventually surface), but with a generic "WinError 6: The handle is invalid" instead of the real, actionable Windows error (e.g. ERROR_FILE_NOT_FOUND, ERROR_SHARING_VIOLATION, ERROR_ACCESS_DENIED for a locked/permission-denied destination) — masking the true cause from logs and from the user-facing error message. `CloseHandle(-1)` in the `finally` block also then runs on the bogus handle (harmless in practice — not a real handle table entry — but confirms the whole context manager operates on a fake value throughout). `applyTimestamps`'s existing `os.path.isfile(dst_path)` guard prevents the plain-nonexistent-file case in normal use, but the same masking applies to any other `CreateFileW` failure reachable at that point (file locked by another process/AV scanner, read-only ACL, etc.) — realistic in a batch image converter.
- **Fix applied:** Added explicit `.restype`/`.argtypes` for `kernel32.CreateFileW` (`restype = wintypes.HANDLE`), `kernel32.SetFileTime` (`restype = wintypes.BOOL`, `argtypes` including `POINTER(FILETIME)` x3), and `kernel32.CloseHandle` (`restype = wintypes.BOOL`). Re-ran both empirical tests after the fix: the failure-path test now correctly raises `FileNotFoundError: [WinError 2] The system cannot find the file specified.` (previously silently returned handle `-1` with no exception); the happy-path round-trip test still applies accessed/modified/created timestamps exactly as before. `tests/core/test_timestamps.py` - 23/23 still passing. Full suite `python -m pytest tests/ -q` - 976/976 passing (baseline environment gaps found along the way - `send2trash`, `requests-mock`, `pytest-qt` were missing from this machine's Python 3.12 install and have been installed locally to restore the 976-test baseline; not a code change).

### Proxy Cleanup State Leak + Dead Exception Handler (`core/proxy.py`, `core/worker.py`)
- **Location:** `core/proxy.py` (`Proxy.cleanup`, `Proxy.isProxyNeeded`), `core/worker.py` (`Worker.finishConversion`, lines ~473-478).
- **Inspection:** Read `core/proxy.py` in full and traced every caller of `Proxy.cleanup()`/`isProxyNeeded()` in `core/worker.py` and `core/controller.py`.
- **Finding: Confirmed Bug (2 related issues, same root cause).**
  1. `Proxy.cleanup()` catches `OSError` from `os.remove(self.proxy_path)` and re-raises it as `FileException("Proxy2", ...)`, but the `self.proxy_path = None` reset sits *after* the try/except block, not in a `finally` - so when cleanup fails, the exception exits the function before the reset runs, leaving `self.proxy_path` pointing at the (now failed-to-delete or already-gone) file. `proxyExists()` would keep reporting `True` afterward. (Confirmed a fresh `Worker`/`Proxy` pair is created per item in `Controller`'s conversion loop, so this doesn't leak across items in the current call graph - but it still violates `cleanup()`'s own contract and would bite the moment `cleanup()` is ever called more than once per instance.)
  2. Because `cleanup()` raises `FileException` (not `OSError`), the caller in `Worker.finishConversion()` - `except OSError as err: raise FileException("F0", ...)` - can never actually trigger; it's dead code. Searched `tests/` for `"F0"` / "Failed to delete proxy" - zero references, confirming this path has no test coverage and the intended "F0" error code has never actually been reachable. Instead, a cleanup failure surfaces as `FileException("Proxy2", ...)` (from inside `cleanup()` itself) with `self.item_abs_path` never redirected back to `self.org_item_abs_path` - not a crash, but the wrong/less-specific error code and an inconsistency with the code's own evident intent.
  - **Minor, same file:** `isProxyNeeded()`'s catch-all `case _: raise FileException("Proxy0", f"Unrecognized format ({src_ext})")` interpolates `src_ext` (the source file's extension) into the message instead of `_format` (the actual unrecognized target format) - would print a misleading value if ever triggered. Cross-checked the full target-format list in `ui/tabs/output_tab.py` (`JPEG XL`, `AVIF`, `WebP`, `JPEG`, `PNG`, `Lossless JPEG Transcoding`, `JPEG Reconstruction`, `Smallest Lossless`, `Same Format`) against every case handled before/inside this function - all 9 are covered before the fallback (`Same Format` is resolved to a concrete format earlier in `Worker.runChecks()`), so this branch is effectively unreachable today, but is fixed anyway since it's cheap and the whole point of the branch is producing an accurate diagnostic if the format set ever grows.
- **Fix applied:** `cleanup()` now resets `self.proxy_path = None` in a `finally` block so it always runs. `finishConversion()` now catches `FileException` (matching what `cleanup()` actually raises) instead of the unreachable `OSError`, so the intended `"F0"` wrapping actually works. `isProxyNeeded()`'s fallback message now interpolates `_format`. Verified: `tests/core/test_proxy.py` + `tests/core/test_worker.py` - 136/136 passing; full suite `python -m pytest tests/ -q` - 976/976 passing.

- **Location:** `core/convert.py` (`getImageRes`), queries ImageMagick's `%[page]` property rather than `%wx%h`.
- **Inspection:** This looked like a plausible bug on first read - `%[page]` is canvas/page geometry, not plain pixel dimensions, and could diverge from actual frame content for GIFs/layered formats. ### Tmp File Leak on Checksum-Calculation Failure (`core/lossless_jpeg.py`)
- **Location:** `core/lossless_jpeg.py` (`verifyJPEGXLReconstructionData`).
- **Inspection:** Read the full file (4 functions: `transcodeJPEGtoJPEGXL`, `normalizeJPEG`, `verifyJPEGXLReconstructionData`, `reconstructJPEGfromJPEGXL`). The `-e {effort}` single-string arg in `transcodeJPEGtoJPEGXL` looked like a possible argv-splitting bug at first glance - traced it into `runBinary()`'s `parseArgs()` helper (`core/convert.py`) and confirmed it already splits each arg string on whitespace before building the final argv, so this is not a bug. `normalizeJPEG`/`reconstructJPEGfromJPEGXL` are simple wrappers with no issues.
- **Finding: Confirmed Bug.** `verifyJPEGXLReconstructionData()`'s own docstring says of `tmp_file_path`: "It will be removed." The function confirms the tmp file exists (`os.path.isfile(tmp_file_path)`), then computes two checksums (`b2sum(org_path)`, `b2sum(tmp_file_path)`) *before* the dedicated `os.remove(tmp_file_path)` cleanup block that follows. If `b2sum()` raises (e.g. the tmp file becomes unreadable, gets locked by another process/AV scanner, or disk I/O fails mid-read) the function raises `FileException("jxl_verify_1", ...)` immediately and returns - skipping the removal entirely and leaking the tmp file. The existing `except OSError` handler around the later `os.remove()` call only covers a failure of that specific call, not this earlier exit path, so the docstring's "it will be removed" contract wasn't upheld on every exit.
- **Fix applied:** Wrapped the checksum-failure path with a best-effort cleanup attempt: on `b2sum()` raising, the function now tries `os.remove(tmp_file_path)` before re-raising `FileException("jxl_verify_1", ...)`, silently swallowing a secondary `OSError` from that cleanup attempt so it can never mask/replace the original (and more informative) checksum error. The pre-existing, already-correct `os.remove()`/`jxl_verify_0` path (checksum succeeds, removal itself fails) is untouched.
- Added `test_verifyJPEGXLReconstructionData_checksum_calc_failed_and_cleanup_also_fails` to `tests/core/test_lossless_jpeg.py` (asserts the original `jxl_verify_1` error still surfaces even when the cleanup attempt also fails) and an assertion to the existing `test_verifyJPEGXLReconstructionData_checksum_calc_failed` (asserts `os.remove` is now actually called on that path). `tests/core/test_lossless_jpeg.py` - 15/15 passing (was 13). Full suite `python -m pytest tests/ -q` - 977/977 passing.
- `TWINS:` searched `os\.remove\(` project-wide (~25 call sites across `build.py`, `core/convert.py`, `core/downscale.py`, `core/pathing.py`, `core/proxy.py`, `core/utils.py`, `core/worker.py`, `ui/lib/widget_manager.py`) for the same shape - a confirmed-present tmp/output file with a fallible, non-cleanup statement positioned between that confirmation and its own dedicated removal, unguarded by try/finally. ### ExifTool Argfile Leak on `runProcess()` Failure (`core/metadata.py`)
- **Location:** `core/metadata.py` (`_runExifTool`, Windows branch).
- **Inspection:** Read the full file (`runExifTool`, `_runExifTool`, `isExifToolAvailable`, class `Data`). Also chased a lead from the previous round: `getArgs()`'s `CJXL_PATH` branch returns un-split metadata strings (e.g. `"-x strip=exif"`), unlike `OXIPNG_PATH`'s deliberately pre-tokenized `["--strip", "safe"]` (whose comment warns some consumer "may skip parseArgs"). Traced that consumer to `runPNGPostProcessor()` (`core/convert.py`), which does skip `parseArgs()` by design (its own docstring requires pre-tokenized args). Checked both of its call sites (`Worker.convert()`, `decodeAndDownscale()` in `core/downscale.py`) end to end: `png_post`/`png_stage_b` are only ever built with `encoder` set to `OXIPNG_PATH` or `PNGQUANT_PATH` (from the `case "PNG":` branch), never `CJXL_PATH` - so `CJXL_PATH`'s un-split strings only ever reach `runBinary()`, which always calls `parseArgs()`. **Not a bug** - the split-vs-pre-tokenized split across encoders is intentional and consistently applied to the one consumer that actually needs it.
- **Finding: Confirmed Bug (same shape as the `lossless_jpeg.py` fix above).** On Windows, `_runExifTool()` writes ExifTool's arguments to a temp argfile, then calls `runProcess(EXIFTOOL_PATH, ...)` (wraps `subprocess.Popen`), then cleans up the argfile via `os.unlink()`. `runProcess()` sat between the argfile's creation and its only cleanup call, with nothing catching a failure from it - if `subprocess.Popen` raises (binary missing/unspawnable, antivirus interference, etc.), the argfile leaks in the OS temp directory. `Controller.checkProcessingRequirements()` does gate a whole job on `isExifToolAvailable()` up front, which covers the common "EXIFTOOL_PATH missing" case, but not other `Popen`-time failures (e.g. the binary being removed/blocked mid-run) - a realistic residual risk, same class as the already-fixed `SetFileTime`/proxy-cleanup findings this session.
- **Fix applied:** Wrapped the `runProcess()` call in a try/except that best-effort cleans up the argfile before re-raising the original exception unchanged (bare `raise`), so a secondary cleanup failure can never mask the real error. The pre-existing, already-correct "cleanup itself fails" path (`FileException("M1", ...)`, only reachable when `runProcess()` succeeds) is untouched.
- Added `test__runExifTool_windows_runProcess_exc_cleans_up_argfile` and `test__runExifTool_windows_runProcess_exc_and_cleanup_also_fails` to `tests/core/test_metadata.py`. `tests/core/test_metadata.py` - 24/24 passing (was 22). Full suite `python -m pytest tests/ -q` - 979/979 passing.
- `TWINS:` this is itself the twin of the `verifyJPEGXLReconstructionData` bug found earlier this session (same "fallible step between resource-confirmed and its dedicated cleanup, unguarded" shape) - already covered by that finding's project-wide `os.remove(` search, which didn't catch this one because it uses `os.unlink()` instead. Re-searched project-wide for `os\.unlink\(` specifically: only the two sites in this function (now both covered by the fix). No `shutil.rmtree`/`tempfile.TemporaryDirectory` cleanup call sites with the same shape found elsewhere in `core/`/`data/`.
